# Mellum 并行计算与精度验证

日期：2026-11-05。目标是恢复实际跨请求计算，同时保持“32 条活动请求输出对 HF 逐条参考”的 token 一致性。本轮只做固定 10 条、32 条短测，每条输出 64 token，没有恢复已停止的全量任务。

**已得到可用的部分并行候选 `norm_cap8`：固定 10 条 640/640，固定 32 条 2048/2048，32/32 条完整一致。** decode 阶段整个批次共同执行原 Qwen3-MoE 骨干；MoE 按专家合并不同请求的 token，每次专家矩阵计算最多处理 8 行。实际记录中外层 decode 批大小达到 32，专家合并前最多 32 行，计算小批最多 8 行。

这次确实有跨请求的专家矩阵计算，不只是调度器维持 32 条在途。但尚未把所有操作都恢复为 vLLM 常规路径的大批计算，也没有证明任意输入的输出都不随批大小变化。

## 当前并行到哪一步

| 环节 | 当前候选行为 |
|---|---|
| Prefill | 每个请求整段独立计算，不 padding、不分块 |
| Decode 骨干 | 32 条请求共同进入一次继承的 `Qwen3MoeModel.forward`，逐层推进 |
| Norm | 保持逐请求计算；单独合并这一部分的候选尚未通过短测 |
| Q/K/V、o_proj、router gate、LM head | 保持逐请求 `F.linear`；简单合并或使用 BMM 的消融未过线 |
| RoPE、残差等操作 | 在 decode 批次上执行 |
| Attention | 使用已有 Attention 组件和 HF 兼容 eager 后端；保留按原长度分组的处理，不启用原生 SWA 加速 kernel |
| MoE 路由和分组 | 跨请求计算路由，将同一专家的 token 收集到一起 |
| 专家矩阵计算 | 每个专家的输入拆成最多 8 行的小批，真实合并多个请求计算；不同小批仍依次调用 |
| 专家激活与输出合并 | 跨请求处理激活；使用既有 Triton kernel 按升序专家、BF16 加权和累加边界还原各请求输出 |

模型、Decoder 和 MoE 容器继续复用 Qwen3-MoE 的 forward、原参数对象和权重加载。专家计算保留 Torch GEMM 与已有有序归约，并未切换为原生融合专家 kernel。21 层 1024 滑窗、7 层全局注意力配置保持。

## 消融与结果

HF 参考固定为冻结 Torch 2.10、原生 Transformers 5.20.2、BF16、eager attention/eager experts、greedy、逐条、无 padding、整段 prefill、ignore EOS。比较原始 token ID，不能用文本相似或功能正确替代。

| 组合 | 10 条结果 | 32 条结果 | 结论 |
|---|---:|---:|---|
| 原有完整逐请求计算对照 | 前轮 640/640 | 本轮 2048/2048 | 精度对照 |
| 骨干按批推进，投影/专家仍逐请求，norm 合批 | 564/640 | 未扩大 | 未过线 |
| 上项额外合并 QKV | 261/640 | 未扩大 | 未过线 |
| 恢复逐请求 norm，其他敏感矩阵保持逐请求 | 640/640 | 2048/2048 | 通过快速集 |
| 上项合并有效窗口相同的 attention | 299/640 | 未扩大 | 未过线 |
| 上项把投影改为 BMM | 232/640 | 未扩大 | 未过线 |
| 上项不限制每个专家的矩阵行数 | 640/640 | 975/2048，7/32 条完整一致 | 大批未过线 |
| 专家矩阵每次最多 1 行，其他 MoE 操作合批 | 640/640 | 2048/2048 | 保守对照 |
| **专家矩阵每次最多 8 行** | **640/640** | **2048/2048，32/32 完整一致** | **当前候选** |

因此，不能因为 10 条通过就推断 32 条也通过。不限制专家矩阵大小的版本正是在扩大测试中失败；将每次矩阵计算限制为 8 行后，本轮 32 条恢复一致。

这些结果支持保留敏感操作边界、控制专家 GEMM 形状的实现选择，但不是所有误差源的数学证明。两个抽样 decode 步的逐层串行/批量对照中，记录的张量恰好全部相同；它们未捕获首次数值分叉，不能据此宣称已定位到某层某个 norm kernel。失败的 attention/BMM 消融也不作为原生算子错误的证明。

## 性能测量范围

首轮短程生成耗时：完整逐请求对照约 126.67 秒；骨干合批、敏感算术独立约 100.01 秒；专家矩阵最多 1 行约 78.00 秒；最多 8 行约 66.06 秒。部分运行在不同 GPU 或有另一张卡的任务同时运行，这些数据只作诊断，不据此发布正式加速比。

随后在 GPU0 上顺序运行两版，另一张卡空闲，得到同卡对照：

| 版本 | 32 条生成耗时 | 原始 token 一致数 | 完整相同请求 |
|---|---:|---:|---:|
| 完整逐请求计算 `serial_control` | 128.681 秒 | 2048/2048 | 32/32 |
| 部分并行 `norm_cap8` | 61.262 秒 | 2048/2048 | 32/32 |

**这组短测约快 2.10 倍，耗时减少 52.39%。** 耗时从调用生成到收集结果，不包含模型加载。该候选两次 32 条测试均保持 2048/2048；同卡性能只有一组顺序对照，未统计多轮方差。

所有这些都是固定 32 条真实 A 输入、每条 64 输出的直接 Engine.generate 测量，不是固定 1024/256 场景，也不是完整 A512、HTTP 32 并发或 600 token/s 验收。

## 文件与入口

新增入口：`/workspace/run_mellum_parallel_precision.sh`，默认 `norm_cap8`。

```bash
CANDIDATE_GPU=1 SERVER_PORT=8580 MELLUM_PARALLEL_MODE=norm_cap8 \
  bash /workspace/run_mellum_parallel_precision.sh --port 8581
```

| 文件 | 作用 |
|---|---|
| `/workspace/tools/mellum_parallel_precision/install.py` | 复用前轮组件安装，切换 decode 为一次批次骨干调用，隔离敏感算术，限制专家矩阵小批大小，记录实际路径 |
| 同包 `attention.py` | 合并有效 KV 长度相同的 attention 消融，结果未过线，默认不启用 |
| 同包 `audit.py` | 在两个抽样步骤中对照串行与批量的中间张量，仅诊断使用 |
| 同包 `__init__.py`、`serve.py`、`README.md` | 导出安装方法、服务接入和使用说明 |
| `/workspace/run_mellum_parallel_precision.sh` | 固定单卡、BF16、level 0、eager、关闭 MTP/TBO/prefix cache/分块的启动入口 |
| `/workspace/results/mellum_parallel_precision_20261105/code/run_stage.py` | 固定集生成、对 HF 计分、实际批次与组件调用计数 |
| 同目录 `code/review.py` | 独立复算原始 token、参考输入、调用路径、旧文件哈希和 Git 状态 |
| 实验根目录 `paired.sh` | 等待前序短测结束，在同一 GPU 上顺序运行原版与候选 |

服务启动脚本已提供，本轮生成测试使用 Engine.generate，没有单独验证 HTTP 服务性能。原朴素版、前轮组件复用版、旧精度版、速度版、公共框架源码和依赖保留；没有 Git 提交。默认交付脚本没有替换为新候选。

固定 32 条通过仅说明这个快速集满足目前精度条件，不能宣称完整 200 条或所有并发输入已经通过。后续扩大验收与进一步合并 QKV/attention 应分别进行。
