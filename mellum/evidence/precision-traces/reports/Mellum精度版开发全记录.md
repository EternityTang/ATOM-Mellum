## 2. 必须先分清的版本、数据和“正确性”

这几天反复出现“以前不是 100% 吗”“以前不是 600 token/s 吗”，并不全是模型退化。部分是真实回退，另一部分来自我们改变了参考、数据或执行方式。我早期的简称和进度表达没有始终讲清这些边界，这是需要记录的问题。

### 2.1 我们至少使用过三套不同的“200 条”

| 名称 | 输入与用途 | 在文中如何使用 |
|---|---|---|
| 最初开发代码题 200 | HumanEval 164＋MBPP 36，自行获取并冻结；通常短输入、各生成 64 token | 用于最初适配和旧 SDPA 参考，不能冒称题方指定的 200 条 |
| A200 | 原场景 A 前 200 条真实变长输入，后来独立以 HTTP 并发 32 运行 | 当前主要精度门槛；生成 256、比较前 64 |
| C200 | 原场景 C 的 200 条长输入，约 4k—16k | 0.30 请求/秒开放到达的性能测试；历史还做过对不同 HF 参考的一致性诊断 |

固定困难 10 条、快速 32 条用于定位和筛选，不能替代完整 200。约 16k 四条单独过线，不能与 A200 合并后用平均数掩盖长输入失败。当前长输入组包含先前触发问题的 C-0009 和最长的三条；推理实现不读取这些题号来选择答案或精度路径。

### 2.2 “eager”曾经被我混用，后来才彻底分开

引擎 `enforce_eager`、编译等级 0、HF attention=eager、HF experts=eager，是不同开关。引擎 eager 仍可显式调用融合专家；experts=eager 也不代表 attention 没有走 SDPA。

早期多轮参考实际是 **Transformers 5.10.1、SDPA attention、eager experts**。我用“HF eager”概括过它，与你要求原生 eager attention 的意思不完全一致。后来审计明确这一点，统一为 **原生 HF 5.20.2 eager attention/eager experts＋冻结 Torch 2.10**。更换参考后的结果必须重新测，旧 100% 不自动继承。[S01]、[S12]、[S13]

### 2.3 我们实际检查过四种不同性质的问题

1. **自身稳定性**：同一个实现、同一输入重复运行，输出是否相同。
2. **相同输入的组件数值**：给两个算子完全相同的张量与权重，结果在哪里不同。
3. **自由生成 token 一致率**：两端各自生成，逐位置比较原始 ID；一次分叉会使后续前缀不同。
4. **功能或性能**：HumanEval 能否执行通过，以及 A/B/C 的吞吐和延迟。

采样稳定不等于与 HF 相同；组件误差很小不保证 greedy token 相同；同 HF 前缀的单步命中率不能代替自由生成；HumanEval 通过不能替代 token 一致性。后面每次重要转向，基本都来自这些检查给出了不同答案。

## 5. 阶段三：先修采样确定性，再发现融合专家是另一条独立问题链

### 5.1 temperature=0 不能只凭参数就认定正确

你要求挑最大差异 prompt、一卡 ATOM 一卡 HF，并后来要求固定最差 10 条快速迭代。两端分叉之外，ATOM 自身重复运行也出现变化。

我用固定 logits 检查 sampler，发现无 top-k/top-p 的路径可能绕过整批 greedy 判断，并列最高分不能保证严格固定选择。模型之外的改动原本受你限制，因此我先准备补丁；你明确批准公共 sampler 修复，又要求参考 v0.1.7。

最终覆盖整批 greedy、混合温度批次和 ModelRunner 将零温度钳到 EPS 的情况，用 `torch.argmax` 保证并列时选较小 ID。冻结 AITER 没有上游对应接口，没有为此升级依赖。朴素 quick10 重复稳定，但仍只有 361/640、3/10 完整一致，说明采样修复不能替代模型数值修复。[S03]

### 5.2 修好 sampler 后，原生 FusedMoE 仍然不稳定

融合专家来自复用的 `Qwen3MoeSparseMoeBlock`：它本来就构造 FusedMoE 容器，原路径会进入 AITER `fused_moe`。这个事实回答了你“融合专家从哪里来”的追问。

在 HumanEval/120 上，同一 271-token 输入重复 16 次生成，前五个 token 相同，第六个在 complete/implement 间变化，分别 5 次、11 次。逐层重复对照最早变化在 **L00 MoE 输出**；此前 embedding、norm、QKV、attention、router logits、MoE 输入均相同。96 个采样检查位置的 token 都等于当次 logits.argmax。

进一步固定 hidden、权重、专家 IDs、路由权重，直接重放融合专家 24 次：后 23 次均与首次不同，最大绝对差 0.03125。这证明问题已到专家计算/合并函数路径，不能再归因 sampler。[S04]

**证明边界。** 我没有证明内部某条指令、原子累加或工作区是唯一根因，不能写“所有 FusedMoE 都有错”。vLLM 使用的融合专家路径也不一定等于这一条。

**我的工具错误。** 早期按每六次预测切分请求，忽略额外计算但不返回的预测，造成跨请求错位。我作废该记录，改按实际 prefill 边界分组，再与客户端 16×6 输出核验。采用的是修正后证据，诊断工具修复不算模型加速。

### 5.3 你的建议促成局部替换，而不是连骨干一起推倒

你要求比较现有朴素版与“保留原生骨干、只替换专家计算”的版本。我新增局部 `TorchExpertMethod`，保留参数容器和 loader，跳过 AITER 的权重 shuffle，以标准权重布局执行 Torch 专家。

HumanEval/151：朴素版 6/64，替换专家版 62/64，后者重复稳定；但完整旧开发集只有 9439/12800＝73.7422%，99/200 完整一致。因此保留这条稳定路径，继续查 norm、路由和 attention，没有把单题改善包装成整体修好。[S05]

类名仍可能叫 FusedMoE，但 forward 已换成 Torch 专家。此后“是否复用容器”和“是否运行融合 kernel”必须分别回答。

## 6. 阶段四：你的四项结构风险检查，发现真实 SWA 边界与多处数值边界

### 6.1 四项结构风险并非全部都成立

你主动列出 RoPE 配置读取、滑窗误作全局、MoE 层选择和专家权重映射四项风险。我做逐层/权重审计，确认当前 checkpoint 的层选择和映射已适配；滑窗配置没有整体丢失，不能把后续低一致率统称为“没有开 SWA”。[S02]

但 SWA 后端接口对窗口的定义确实不同。最初我判断 prefill 多看一个 key、decode 正确；这个结论有漏测：只检查了过期 key 排除，没有检查最早合法 key 保留。

补带标记 key 的 GPU 边界用例后，发现冻结 Gluon decode 直接传 W 也会漏 key。最终在调用层做语义换算：prefill 左距离 W−1，冻结 Gluon decode 按其实际定义传 W＋query_len。模型窗口始终是 1024。53 个实际 GPU 用例通过，相关插件调用同步修正。[S06]

当时困难十条的输入加输出不足窗口长度，不能用它们的 token 改善或退化来证明 SWA 修复效果。这是我需要主动说明的证据范围。

### 6.2 路由权重 dtype 修复有效，却不足以一次解决

HumanEval/5 中，将归一化路由权重从 FP32 转回 BF16，一致位置从 7/64 提升到 46/64。保留 FP32 softmax/top-k/归一化，再在与 HF 对应的位置转 BF16。

你要求一张卡继续查，另一张卡跑 BF16 全量；后来又要求停止全量，任务停在 96 条，记录为 `stopped_by_user`。未完成的结果没有冒充完整 200，也没有在后来其他实验中擅自恢复。

后续同输入检查还发现 top-k 的有序列表会影响每个专家的输入行顺序。固定路由、权重和排列，专家步骤 56/56 逐值一致；使用原生排列只有 45/56。决定继续保留 HF 的路由顺序，而不是直接重写已经通过同输入检查的专家公式。[S02]

### 6.3 RNE 是一次必须保留的负向实验

你要求每层 hidden/logits 对比，我选择最差样本 HumanEval/61。首差在 L00 input norm。核对实际 dispatch 后，发现当时 OPUS norm 使用 RTZ 截断；残差融合还存在“FP32 和先参与归约”与“先舍入 BF16 再归约”的差别。

我实现局部 RNE norm 两种顺序，保留 113 处原参数。HumanEval/61 从 5/64 改善到 51/64，但完整固定十条从 356/640 降至 native 顺序 320/640；HF 顺序也只有 327/640。最终保持早期 RNE 开关默认关闭。[S07]

实验本身有价值，错误会出在据单题改善建议整体切换。实际是固定十条推翻了这个推广。后来的最终精度组合使用明确定义的 norm/残差路径，也不等于这次早期 RNE 开关后来自动转正。

## 7. 阶段五：朴素版也不准，最终发现“数学等价”不足以保证 token 相同

**你的质疑。** 既然复用融合算子会有误差，为什么朴素 Torch 实现也差这么大？你要求直接修朴素版，并跑完整测试。

**固定输入实验。** 在 HumanEval/151 保存完全相同 Q/K/V 重放：朴素版始终显式加 mask，让 Torch 2.10/ROCm 选择 Efficient Attention；旧 HF 的 causal/GQA 调用走 Flash Attention。可见范围相同，数值实现不同。[S08]

**修复。** 可安全省 mask 的整段 causal prefill 使用 `attn_mask=None` 与 causal/GQA；单 token 全可见 decode 使用非 causal；带历史多 query 或真正的窗口边界仍保留显式 mask，避免把矩形缓存 attention 错交给左上角 causal 语义。

**验证与取舍。** 168/168 attention 重放逐元素相同；固定十条从 361/640 提高到两轮 640/640，随后旧代码题 200 条 12800/12800。保留此朴素实现作为旧 SDPA 参考的可信基准。

### 12.1 我们究竟审查了什么

### 12.2 A-0126 的同输入回放改变了判断

A-0126 输入 3857 token。单条、整段、无 padding 时，HF 与 ATOM 前八步的 **3696 个记录张量逐位相同**。改成分块或批量，差异已经在第 0 层 Q/K/V 投影出现。

当时没有追到具体 hipBLAS kernel ID，不能进一步写成某个已命名内核必然是唯一根因。也不能保证“全改 FP32”就一定更像原生 BF16 HF。

### 12.3 第二类 SWA 问题：mask 可见性正确，参与计算的矩阵长度仍不一致

我修正 `eager_one()` 的历史裁剪：全局层不裁，SWA 只去掉对当前整块都不可见的历史。修后同样四个 prefill 块＋七个 decode 的 **5082 个记录张量逐位一致**；单条整段与单条分块各十条都 640/640。[S15]

这与前面冻结 Gluon 的窗口传参修复是两件事：一个是窗口边界是否正确，另一个是精度 eager 路径的 KV 计算范围是否匹配 HF。修完后批处理/padding/GEMM 形状差异仍存在，不能说“找到 SWA 后所有问题都解决”。

保持每个专家 GEMM 形状/顺序，合批 SiLU/up、加权和归并，长输入 256/256；Triton 融合 score 缩放/mask、保留原 Torch FP32 softmax，也 256/256。对应诊断长生成约 31.90、29.68 秒，仍需进一步减少热点。

随后直接把大形状 softmax 换 BF16 输出，随机组件仅数十元素不同，自由生成却长输入 **117/256＝45.70%**。这一负例解释了为什么我们不能在看到相对误差很小后就接受一个 attention 变体。

### 21.5 根据长 prefill trace，转向复刻冻结 Torch 的归约顺序

15194-token 单请求 prefill 的旧 trace 中，GPU kernel 累计约 5156 ms：FP32 softmax 约 1345 ms，另有约 481 ms BF16→FP32、383 ms FP32→BF16、607 ms mask、328 ms 缩放。GEMM 也很重，但非 GEMM 路径值得融合。

CPU `bincount` 看起来等待很长，不能直接算成专家自身计算时间，因为它包含等待之前排队 GPU 工作的时间。我们依据 GPU correlation 和真实执行链选方向，没有仅按 CPU 排名决定重写专家。

我读取冻结 Torch git 提交 `3d3aa833db84eed6b7f5595cb5f162c2f78300a4` 的 SoftMax 源码，保留其大形状 FP32 softmax 的 512 线程、ILP4、对齐处理、指数及 BlockReduce 顺序，融合 BF16 score 缩放/舍入、mask 和最终输出转换。原 Torch QK/PV GEMM 保留，不替换 Torch 二进制或安装版本，保留来源及许可证。

之所以不是直接用大形状 BF16 softmax，是其 kernel 组织/ILP 与原 FP32 路径不同。我们要优化数据搬运和派发，不能把刚验证失败的归约变化又带进来。

首轮 HIP 扩展被 hipify 对同一行 if/else kernel launch 的解析问题卡住；改为独立带花括号语句才编译通过。编译修复只是实现问题，精度仍需另外验收。

8 组 global/SWA 组件、长度 2049/4096/15194/16019，共 **1,016,883,228 个概率元素**全部逐位相同；长输入生成 256/256，约 20.03 秒。它们是有限测试结果，不能宣称对任意输入都已形式证明。

## 22. 为什么现在的精度版仍慢，以及现在到底算几个优化点

当前精度版仍对齐冻结 Torch 的 HF BF16 数值路径，保留较多敏感 GEMM 形状、Torch 专家 cap8、部分逐请求 attention 和完整长 prefill 矩阵。原生速度版则可采用另一套原生分页 attention、融合专家和更大 Graph 组织；它的速度或 HumanEval 结果不能当作精度版验收成绩。

C 修复降低了转换/softmax/派发，并保护在途请求，却没有把全部长输入矩阵计算变成稀疏窗口算法。TTFT p99 仍 96.57 秒，TPOT p99 468.72 ms；因此“C 超时解决”与“C 性能合格”必须分开。最新同一候选完整 A512/B50 尚未重跑，HumanEval 本轮也未重跑。

目前有完整工程消融的三个主点仍为 **直接分页/GQA KV、Norm 合批、局部 HIP Graph**；工程底座另有 cap8、滑窗 softmax 和 prefill 稳定路由。后来 C 又增加精确 softmax 融合与调度策略。

精确 softmax 融合可以成为新算子候选点；fair4＋年龄保护属于调度方向。不能把它们简单塞入“KV 读取”名下，继续声称严格仅三点。最终若要求只保留三个，需要重新明确起点、范围和组合，用同底座完整 ABC 决定，而不是因某个新点看起来快就口头换名额。现阶段不预先宣布哪三个能同时满足所有要求。

### 23.1 各阶段时间线的文字示意

以下仅表示执行组织，长度不按真实毫秒比例绘制；数值以表格与原始 trace 为准。

```text
早期复用精度 decode：
CPU  发起小算子 → 收集/展开每请求KV → SDPA → 下一个请求 → 专家循环 → ...
GPU  小kernel --间隙-- copy/index --间隙-- attention --间隙-- 小GEMM ...

局部 Graph：
CPU  准备输入 → 一次局部图回放 → 动态attention/路由 → 下一局部图 ...
GPU  图内原算子连续运行；kernel数未必变，主机逐次发起明显减少

Norm 合批：
GPU  多个重复逐元素kernel → 更少的合批kernel；原敏感归约先保留

GQA 共享读取：
GPU  同一KV head反复读8遍 → 读一次、写出原布局；后续QK/PV保持

旧 C 调度：
请求A首token → 长prefill B → 长prefill C → 长prefill D → A后续decode很少

C 公平/年龄保护：
prefill → 留出decode步 → prefill；请求年龄较大时先推进已有decode
```

### 23.3 中间测量也犯过错，如何防止结论建立在错误工具上

一是请求边界错位和 RoPE hook 漏录，前文已记录。二是优化开关被 launcher 覆盖，后来以 runtime 与真实调用次数作准。三是部分性能初筛存在同卡其他任务，保留原记录并重新做空闲顺序对照；trace 的事件组织仍可用于机制分析，重叠时长不拿来发布加速比。
